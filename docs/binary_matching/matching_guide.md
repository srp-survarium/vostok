## Tools

Considering that all prerequisites were installed, you should have everything for matching the assembly.

The main tool that will be needed is IDA. Its usage is pretty extensive, and I will not cover it here.

You would also need `objdiff` for comparing `target` and `base` object files. `target` here refers to the actual game (what we are targeting) and `base` refers to our decompilation project.

It makes sense to have two instances of IDA running at the same time. One for `target` executable and one for `base` executable. No need to analyze `target` executable. There are links to the most recent version of the database I already worked on. `base` executable, on the other hand, needs to be reanalyzed every single time you recompile the project. (Doing this is not required every single time the project is recompiled, do it only when you need to match two versions of the resulting assembly from IDA and objdiff is not enough).

I would also recommend installing `ripgrep`, as I found myself grepping for different things a lot, and `ripgrep` is fastest at that.


## SRP projects

The game was shipped with the `.pdb` files attached. The debug symbols store information used by the debugger to annotate the assembly and generate breakpoints. What it allows us to do is, given the `.pdb` file, recover structure of the original source code. In the structure we will see function signatures, arguments, block starts and, most interestingly, lines in the original source code where you were allowed to set breakpoints (which are usually statements in the source code).

This structure is generated by the `pdb-parser` script in the `srp` repository and the most recent version is stored in the `vostok-structure` repository.

For example, take a look at `box_geometry_instance::get_closest_point_to` function [here](https://github.com/srp-survarium/vostok-structure/blob/v0.100b/sources/collision/sources/box_geometry_instance.cpp#L473).

You will see this "carcass":

```cpp
// vostok::math::float3 vostok::collision::box_geometry_instance::get_closest_point_to(vostok::math::float3 const&, vostok::math::float4x4 const&) const
float3 box_geometry_instance::get_closest_point_to(
	float3 const&                      source,
	float4x4 const&                    origin)
{
	// LOCALS
	// float4x4                        transform
	// float3                          dir
	// float3                          half_sides
	// float3                          axis
	// ******

	// FUNCTION BODY
	// <0x24df49>|0x000|0x00|
	// <0x24df5c>|0x013|0x13|
	// <0x24df69>|0x020|0x0d|
	// <0x24dfa2>|0x059|0x39|

	// <0x24e05f>|0x116|0xbd|

	// <0x24e070>|0x127|0x11|
	// <0x24e081>|0x138|0x11|
	// <0x24e0e9>|0x1a0|0x68|

	// <0x24e10c>|0x1c3|0x23|
	// <0x24e11a>|0x1d1|0x0e|

	// <0x24e129>|0x1e0|0x0f|



	// ******
}
```

A few things stand out:
1. The comment with the original function signature without argument names. The way `pdb` files are parsed has flaws and sometimes the arguments it generates are incorrect. The original signature, however, is always correct and can be looked at as a sanity check.
2. Locals arguments in the function. Note that the order doesn't mean anything and that some arguments could have been compiled out.
3. Function body. If there is an empty line, that means that a breakpoint couldn't be set in that place. This can be because of the empty lines, comments, ifdefs or optimized statements. Lines where the breakpoints could be set look like this:
```
	// <0x24df49>|0x000|0x00|
    // <0x24df5c>|0x013|0x13|
	// <0x24df69>|0x020|0x0d|
  ...
```
What it tells you is where in the IDA you can find the beginning of the statement (press G in the assembly listing in IDA and paste the address to it (G > 0x24df5c > Ok)). It also shows how far away this statement is from the beginning of the function; and how far away it is from the previous recorded statement. This is useful to understand the scope of the function (will be shown next).

This is how the actual function looks like:
```cpp
float3 box_geometry_instance::get_closest_point_to	( float3 const& source, float4x4 const& origin ) const
{
	float4x4 transform			= origin * m_matrix;           // <0x24df49>|0x000|0x00|
	float3 dir					= source - transform.c.xyz( ); // <0x24df5c>|0x013|0x13|
	float3 result				= transform.c.xyz( );          // <0x24df69>|0x020|0x0d|
	float3 half_sides			= transform.get_scale( );      // <0x24dfa2>|0x059|0x39|

	for (int i = 0; i < 3; i++)                                // <0x24e05f>|0x116|0xbd|
	{
		float3 axis				= transform.lines[i].xyz( );   // <0x24e070>|0x127|0x11|
		axis.normalize			( );                           // <0x24e081>|0x138|0x11|
		float dist				= dir.dot_product( axis );     // <0x24e0e9>|0x1a0|0x68| `normalize` was inlined, hence this big jump 
		
		if (dist > half_sides[i]) dist	= half_sides[i];       // <0x24e10c>|0x1c3|0x23|
		if (dist < -half_sides[i]) dist	= -half_sides[i];      // <0x24e11a>|0x1d1|0x0e|

		result								+= dist * axis;    // <0x24e129>|0x1e0|0x0f|
	}

	return result;                                             // This line was somehow removed by the optimizer
}
```

You can see how well the function fits its `pdb` structure and why this is useful.

Sometimes it makes sense to match not the assembly, but the structure itself. For this `xray-structure` project will always contain the structure of the most recent `base` executable built (it is updated by hooks in VS).


But in general you would look at the `objdiff` output (see the attached image). If the diff is obvious, which is unlikely to be the case, you can understand what changed just from its output, if not, you would use IDA to deeper understand the scope of the problem.


## A few tips regarding assembly matching

* Most of the `target` modules were compiled with linker optimizations enabled. The way those optimizations work are very non-local. They will remove function arguments, if the program analysis shows that the function is used with the same argument everywhere; the calling conventions will be botched and the optimizers will try to use whatever registers are available to pass the arguments instead of the stack. Even in the attached screenshot you can see that `base` assembly doesn't push `0x1` onto the stack and uses registers in `draw_primitives_solid` compared to `target`. Based on everything else the assembly is the same, and I currently do not try to match linker optimizations.

* In non-optimized builds the situations isn't that much better, since any small syntactic change can result in a slightly different assembly, making it really hard to match the `target`.
