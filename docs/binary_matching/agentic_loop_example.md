# Agentic loop - worked example

One **worker's** run (one function) through [`agentic_loop.md`](agentic_loop.md)
end to end - the orchestrator dispatches these sequentially (see "Orchestrator and
workers" there). The **commands** are exactly what the worker runs each iteration;
the read-only outputs below are **real** (run against the prebuilt `binaries/rich`
+ `binaries/objdiff`). The `rebuild.py` build/score lines are from the recorded
build - the actual compile needs the Wine/MSVC toolchain.

Subject: `survarium::collision_sensor::notify_objects_inside` (game_core), already
matched to `STATE[89.29%|PARTIAL]` - a good example because the residual is an
LTCG/inlining artifact that source cannot change.

> **On the percentages.** Both `report.json` (the scoreboard, what `STATE` records)
> and `pdb_fetch --view diff` report a **fuzzy** match - partial credit per
> instruction, so a stack-slot-only difference barely costs anything. They track
> closely (here **89.29%** scoreboard vs **89.61%** from `pdb_fetch`) but are not
> bit-identical, since `report.json` is generated by a different objdiff version.
> Use `report.json`/`STATE` for the number of record, `pdb_fetch` for *where* the
> diffs are. (And `report.json` here was generated under actual MSVC; a local Wine
> rebuild can differ.)

Read it: nearly every `~` is a `[ebp-XX]` stack-slot or frame-size shift - LTCG
artifacts, not bugs (the fuzzy match barely counts them, which is why both numbers
sit near 89%). The one structural difference is the `-` block: base emits an extra
`size()`/fill pass while building the `buffer_vector` over `ALLOCA`, which the
target folded under LTCG. Not steerable from source (MATCHING.md - LTCG;
agentic_loop.md section 5).
